> 在板上的系统脚本里找到了具体冲突：厂商脚本会把这台 `orangepi5ultra` 的 OTG 口设为 `host`，项目的 USB 维护服务则把同一个口设为 `device`。厂商脚本在后台执行，所以即使 systemd 已显示它启动完成，它仍可能覆盖维护服务刚设好的模式。

<a id="m-2-4"></a>

### 助手 2.4

2026-11-26T17:55:57+08:00

> **原因是开机时有两个任务给同一个 USB OTG 口设置了相反的角色。** 项目的 USB 维护服务把香橙派设为 `device`，这样 Windows 才能把它识别为 USB 网卡。厂商的硬件初始化脚本也会在这台 `orangepi5ultra` 上运行，并把同一个口设为 `host`。这段脚本在后台执行，两次设置的先后会影响最终结果。
>
> 这次开机后约 **12.2 秒**，USB 维护服务报告就绪。到 **13.4 秒**，内核记录同一端口已经转为主机模式。板端因此没有建立 `usb0`，配置 `〔网络地址〕` 的服务等待约 20 秒后退出，也没有自动重试。Windows 看不到 USB 网卡，最终表现为 SSH 超时。两处脚本的冲突已核实，本次日志时序也与厂商脚本随后覆盖设置相符。
>
> **最直接的防范办法，是让这个维护口只由一个服务决定角色。**
>
> 1. **消除冲突。** 在这台板启用 USB SSH 维护时，让厂商脚本跳过对该端口写 `host` 的那一行，其余硬件初始化照常执行，由现有 USB 维护服务统一设为 `device`。单纯把维护服务排在厂商服务之后仍有风险，因为 systemd 显示厂商服务完成时，其后台任务还可能在运行。
> 2. **让启动结果可验证。** 维护服务应在确认控制器仍为 `device`、`usb0` 已出现且已配置 `〔网络地址〕/24` 后再报告成功。启动阶段失败时可以有限重试，并记录失败在哪一步。
> 3. **用实际冷启动验收。** 分别测试“接好数据线再开机”和“开机后再插线”，每种情况重复几次。每次从 Windows 执行 `ssh 〔设备别名〕`，确认会话实际走 `〔网络地址〕 → 〔网络地址〕:22`。
